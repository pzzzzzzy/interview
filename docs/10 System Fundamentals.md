## 二、操作系统核心概念

### 2.1 进程 vs 线程 vs 协程

#### 进程 (Process)

**定义**: 程序的一次执行实例，是操作系统资源分配的基本单位。

**特点**:
```
资源隔离:
- 每个进程有独立的地址空间
- 一个进程崩溃不影响其他进程
- 进程间通信需要IPC机制

内存占用:
- 每个进程需要独立的内存空间
- 包括代码、数据、堆、栈

创建开销:
- 创建进程开销大（fork需要复制地址空间）
- 切换进程开销大（需要切换地址空间）
```

**类比理解**:
```
进程 = 一间独立的办公室
- 有自己的桌子、文件柜（内存）
- 和其他办公室隔离
- 沟通需要走廊传话（IPC）
```

---

#### 线程 (Thread)

**定义**: 进程内的执行单元，是CPU调度的基本单位。

**特点**:
```
共享资源:
- 同一进程的线程共享地址空间
- 共享全局变量、堆内存
- 每个线程有独立的栈

轻量级:
- 创建线程开销小
- 切换线程开销小（不需要切换地址空间）
- 但需要处理同步问题（竞态条件）

通信简单:
- 线程间可以直接访问共享内存
- 但需要加锁保护共享数据
```

**类比理解**:
```
线程 = 办公室里的多个员工
- 共享办公室资源（内存）
- 可以直接交流（共享变量）
- 但要注意不要同时改同一份文件（需要锁）
```

---

#### 协程 (Coroutine)

**定义**: 用户态的轻量级线程，由程序自己调度。

**特点**:
```
更轻量:
- 创建开销极小（只是函数调用）
- 切换开销极小（不需要内核参与）
- 一个线程可以有成千上万个协程

协作式调度:
- 协程主动让出CPU（yield）
- 不会被操作系统强制切换
- 适合IO密集型任务

单线程执行:
- 协程在单线程内切换
- 没有真正的并行（除非配合多线程）
- 不需要加锁（同一时刻只有一个协程在执行）
```

**类比理解**:
```
协程 = 一个员工处理多个任务
- 做任务A，遇到等待（IO）时
- 主动切换去做任务B
- 任务B等待时再切回任务A
- 没有真正的"分身"（并行）
```

---

#### 三者对比总结

```
┌─────────────────────────────────────────────────┐
│              进程 vs 线程 vs 协程                │
├─────────────┬───────────┬───────────┬───────────┤
│   特性      │   进程    │   线程    │   协程    │
├─────────────┼───────────┼───────────┼───────────┤
│ 资源隔离     │   完全    │   部分    │   共享    │
│ 创建开销     │   大      │   中      │   极小    │
│ 切换开销     │   大      │   中      │   极小    │
│ 通信方式     │   IPC     │ 共享内存   │ 共享内存  │
│ 数量限制     │   少      │   中      │   极多    │
│ 并行能力     │   真并行   │ 真并行    │ 伪并行    │
│ 适用场景     │ CPU密集   │ CPU密集   │ IO密集    │
└─────────────┴───────────┴───────────┴───────────┘
```

**选择原则**:
```
多进程:
✅ 需要隔离性（稳定性优先）
✅ CPU密集型任务
✅ 充分利用多核
❌ 通信复杂、开销大

多线程:
✅ 需要共享数据
✅ CPU密集型任务
✅ 充分利用多核
❌ 需要处理同步问题

协程:
✅ IO密集型任务（网络、文件）
✅ 需要高并发
✅ 简化异步编程
❌ 不能利用多核（需配合多线程）
```

### 2.2 进程间通信 (IPC)

#### 为什么需要IPC？

进程间资源隔离，但有时需要协作：
```
场景1: PyTorch DataLoader
- 主进程: 训练模型
- 子进程: 加载数据
- 需要传递数据

场景2: 分布式训练
- 多个进程训练同一模型
- 需要同步梯度

场景3: 微服务架构
- 不同服务独立进程
- 需要RPC通信
```

---

#### IPC机制详解

**1. 管道 (Pipe)**

**特点**:
- 单向通信（半双工）
- 父子进程间通信
- 数据流式传输

**Python例子**:
```python
from multiprocessing import Pipe

# 创建管道
parent_conn, child_conn = Pipe()

# 父进程发送
parent_conn.send("Hello")

# 子进程接收
msg = child_conn.recv()  # "Hello"
```

**适用**: 简单的父子进程通信

---

**2. 消息队列 (Message Queue)**

**特点**:
- 异步通信
- 可以多对多
- 消息有类型和优先级

**概念理解**:
```
消息队列 = 邮箱
- 进程A往邮箱里放信
- 进程B从邮箱里取信
- 支持多个进程同时操作
```

**PyTorch DataLoader的实现**:
```
主进程                     Worker进程
  ↓                           ↓
Queue ←─────────────────── 加载数据
  ↓                           
获取batch
```

**优势**: 解耦生产者和消费者

---

**3. 共享内存 (Shared Memory)**

**特点**:
- 最快的IPC方式（直接内存访问）
- 需要同步机制（锁）
- 适合大数据传输

**工作原理**:
```
进程A的地址空间:        进程B的地址空间:
┌─────────────┐         ┌─────────────┐
│   私有内存   │         │   私有内存   │
├─────────────┤         ├─────────────┤
│             │         │             │
│  共享内存区  │ ←─────→ │  共享内存区  │
│  (物理内存)  │         │  (物理内存)  │
└─────────────┘         └─────────────┘

两个进程的虚拟地址映射到同一块物理内存
```

**应用场景**:
```
PyTorch Tensor共享:
- 多进程读取同一个大tensor
- 避免数据复制
- pin_memory就是利用共享内存
```

**注意事项**:
- 需要加锁防止竞态条件
- 需要手动管理生命周期

---

**4. 信号量 (Semaphore)**

**定义**: 用于进程/线程同步的计数器

**核心操作**:
```
P操作 (wait/acquire):
- 计数器 - 1
- 如果计数器 < 0，阻塞等待

V操作 (signal/release):
- 计数器 + 1
- 唤醒一个等待的进程
```

**经典问题: 生产者-消费者**

```
问题描述:
- 生产者: 往缓冲区放数据
- 消费者: 从缓冲区取数据
- 缓冲区大小有限

同步需求:
- 缓冲区满时，生产者等待
- 缓冲区空时，消费者等待
- 同时只能一个线程访问缓冲区

解决方案:
empty = Semaphore(N)  # 空位数量，初始=N
full = Semaphore(0)   # 数据数量，初始=0
mutex = Semaphore(1)  # 互斥锁

生产者:
  empty.wait()     # 等待空位
  mutex.wait()     # 获取锁
  放入数据
  mutex.signal()   # 释放锁
  full.signal()    # 增加数据计数

消费者:
  full.wait()      # 等待数据
  mutex.wait()     # 获取锁
  取出数据
  mutex.signal()   # 释放锁
  empty.signal()   # 增加空位计数
```

**PyTorch DataLoader实际应用**:
```
DataLoader内部使用信号量控制:
- 限制队列中batch的数量
- 生产者（worker）不会无限制地加载数据
- 消费者（训练）不会等待太久
```

---

**5. Socket**

**特点**:
- 支持网络通信（跨机器）
- 可以是本地Socket（同机器，更快）
- 灵活但复杂

**应用**:
- 分布式训练的通信
- RPC调用
- 微服务架构

---

#### IPC方式对比

```
性能: 共享内存 > Socket > 消息队列 > 管道
复杂度: 管道 < 消息队列 < Socket < 共享内存
适用范围: 管道(父子) < 消息队列(本机) < 共享内存(本机) < Socket(网络)
```

**选择建议**:
```
小数据、简单场景: 管道、消息队列
大数据、高性能: 共享内存
跨机器: Socket
```

### 2.3 虚拟内存

#### 什么是虚拟内存？

**核心概念**: 每个进程看到的是独立的"虚拟"地址空间，操作系统负责映射到实际物理内存。

**为什么需要虚拟内存？**

```
问题1: 内存隔离
没有虚拟内存:
- 进程A和B共享物理地址空间
- 进程A可能错误访问进程B的内存 → 崩溃

有虚拟内存:
- 每个进程有独立的虚拟地址空间
- 物理隔离，安全

问题2: 内存不足
没有虚拟内存:
- 物理内存只有8GB
- 无法运行总和超过8GB的程序

有虚拟内存:
- 暂时不用的数据swap到磁盘
- 可以运行更多程序（虽然慢）

问题3: 内存碎片
没有虚拟内存:
- 物理内存碎片化
- 大块连续内存难以分配

有虚拟内存:
- 虚拟地址连续，物理地址可以不连续
- 通过页表映射
```

---

#### 虚拟内存的工作原理

**地址转换**:

```
虚拟地址 (进程看到的)
    ↓
  页表 (映射)
    ↓
物理地址 (实际的RAM)

例子:
进程A:
虚拟地址 0x1000 → 物理地址 0x5000
虚拟地址 0x2000 → 物理地址 0x3000

进程B:
虚拟地址 0x1000 → 物理地址 0x7000
虚拟地址 0x2000 → 物理地址 0x4000

同样的虚拟地址，映射到不同的物理地址
```

**页 (Page) 和页表 (Page Table)**:

```
虚拟内存和物理内存都被分成固定大小的页:
- 常见页大小: 4KB

虚拟地址组成:
┌──────────────┬────────────┐
│   页号       │  页内偏移   │
└──────────────┴────────────┘
     20位           12位
   (4KB页大小下)

页表记录:
虚拟页号 → 物理页号的映射
```

---

#### 页面置换算法

**问题**: 物理内存不够，需要把一些页面换出到磁盘（swap）

**常见算法**:

**1. FIFO (先进先出)**
```
原理: 最先进入内存的页面先被换出
缺点: 可能换出常用的页面
```

**2. LRU (最近最少使用)**
```
原理: 换出最长时间未被访问的页面
思想: 最近用过的，未来可能还会用
实现: 维护访问时间戳或链表

优点: 性能较好
缺点: 实现开销大
```

**3. Clock (时钟算法)**
```
原理: LRU的近似算法
- 每个页面有访问位（1=最近访问过，0=没有）
- 指针循环扫描，遇到0就换出
- 遇到1就置0，继续扫描

优点: 实现简单，性能接近LRU
```

**面试重点**: 
- 理解LRU的思想
- 能描述工作过程
- 知道trade-off

---

#### Swap和OOM

**Swap (交换分区)**:

```
作用: 物理内存不足时，把部分数据换到磁盘

过程:
1. 系统发现内存紧张
2. 选择页面换出到swap分区
3. 释放物理内存给新进程

代价:
- 磁盘访问比内存慢1000-10000倍
- 频繁swap会导致系统卡顿（thrashing）
```

**OOM (Out Of Memory)**:

```
触发条件:
- 物理内存 + Swap都用完
- 系统无法分配新内存

OOM Killer:
- Linux内核的机制
- 选择一个进程杀掉，释放内存
- 选择标准: 占用内存多、优先级低、运行时间短

AI训练中的OOM:
"CUDA out of memory"
原因:
- Batch size太大
- 模型太大
- 中间激活值太多
```

**避免OOM的策略**:
```
1. 减小batch size
2. 使用梯度累积
3. 混合精度训练（FP16）
4. Gradient checkpointing
5. 增加GPU显存
```

### 2.4 CPU缓存与缓存一致性

#### CPU缓存层次

**为什么需要缓存？**

```
速度差距:
CPU寄存器:    0.5 ns    (基准)
L1 Cache:     1 ns      (2×)
L2 Cache:     4 ns      (8×)
L3 Cache:     15 ns     (30×)
主内存 (RAM): 100 ns    (200×)
SSD:          100,000 ns (200,000×)
HDD:          10,000,000 ns (20,000,000×)

相差上万倍！
```

**缓存结构**:

```
CPU Core 0          CPU Core 1
┌──────────┐        ┌──────────┐
│ L1 Cache │        │ L1 Cache │
│  32 KB   │        │  32 KB   │
├──────────┤        ├──────────┤
│ L2 Cache │        │ L2 Cache │
│  256 KB  │        │  256 KB  │
└────┬─────┘        └────┬─────┘
     │                   │
     └─────────┬─────────┘
               │
         ┌─────┴─────┐
         │ L3 Cache  │
         │   8 MB    │
         └─────┬─────┘
               │
         ┌─────┴─────┐
         │    RAM    │
         │   16 GB   │
         └───────────┘
```

**特点**:
- L1/L2: 每个核心独占
- L3: 所有核心共享
- 越靠近CPU越小、越快

---

#### 缓存行 (Cache Line)

**概念**: 缓存的基本单位，通常64字节

**重要性**:

```
连续访问 vs 随机访问:

场景1: 连续读取数组
int arr[16];  // 64字节
for (int i = 0; i < 16; i++) {
    sum += arr[i];
}

第一次访问arr[0]时:
- 整个cache line (64字节) 被加载
- arr[1]...arr[15]也在缓存中
- 后续访问极快（cache hit）

场景2: 随机访问
struct Data {
    int value;
    char padding[60];  // 使每个元素64字节
};
Data arr[16];
for (int i = 0; i < 16; i++) {
    sum += arr[i].value;
}

每次访问都是新的cache line
- 每次都cache miss
- 慢得多
```

**性能影响**: 
```
连续访问: 100倍于随机访问
这就是为什么"数据局部性"很重要
```

---

#### False Sharing (伪共享)

**问题描述**:

```
两个线程访问不同的变量，但这些变量在同一个cache line:

线程1的变量: x
线程2的变量: y
内存布局: [x][y][ ... ] ← 同一cache line

虽然x和y逻辑上独立，但:
- 线程1修改x → 整个cache line失效
- 线程2的缓存需要重新加载
- 线程2修改y → 线程1的缓存失效
- 来回失效，性能大幅下降
```

**解决方案**: Padding

```
struct PaddedData {
    int value;
    char padding[60];  // 填充到64字节
};

现在每个value在独立的cache line中
不会相互影响
```

**PyTorch中的应用**:
```
Tensor的连续性 (contiguous):
- 连续的tensor利用缓存更好
- view操作可能破坏连续性
- contiguous()强制重排列
```

---

#### 缓存一致性协议 (Cache Coherence)

**问题**: 多核CPU，每个核有自己的L1/L2缓存，如何保证一致性？

```
初始状态:
内存中 x = 0

CPU 0 读取 x → L1缓存: x = 0
CPU 1 读取 x → L1缓存: x = 0

CPU 0 写入 x = 1 → L1缓存: x = 1
现在:
- CPU 0 缓存: x = 1
- CPU 1 缓存: x = 0
- 不一致！
```

**MESI协议** (最常用):

```
四种状态:
M (Modified):   独占且已修改，需要写回内存
E (Exclusive):  独占且未修改，和内存一致
S (Shared):     多个缓存共享，和内存一致
I (Invalid):    无效，需要重新加载

状态转换:
读取: I → S/E
写入: E/S → M (其他缓存变为I)
写回: M → E
```

**性能影响**:
```
多线程频繁写入共享变量:
- 不断触发缓存失效
- 性能下降

优化策略:
- 减少共享变量
- 每个线程用私有变量，最后合并
- 使用原子操作或锁
```

### 2.5 中断和系统调用

#### 中断 (Interrupt)

**定义**: 硬件或软件向CPU发出的信号，要求CPU暂停当前任务，处理紧急事件。

**类型**:

**1. 硬件中断**
```
来源: 外部设备（网卡、磁盘、键盘等）

例子:
- 网卡接收到数据包
- 磁盘读取完成
- 键盘按键

特点:
- 异步（随时可能发生）
- 优先级高
```

**2. 软件中断（异常）**
```
来源: 程序执行中的异常情况

例子:
- 除零错误
- 访问非法地址（segmentation fault）
- 系统调用（syscall）

特点:
- 同步（由指令触发）
```

**中断处理流程**:

```
1. 保存现场
   - 保存CPU寄存器
   - 保存程序计数器

2. 执行中断处理程序
   - 快速处理紧急事情
   - 或标记延后处理

3. 恢复现场
   - 恢复寄存器
   - 继续原程序执行

原则: 中断处理要快
- 长时间处理放到中断下半部
```

---

#### 系统调用 (System Call)

**定义**: 用户程序请求内核服务的接口。

**为什么需要系统调用？**

```
用户态 vs 内核态:

用户态:
- 普通程序运行的模式
- 权限受限，不能直接访问硬件
- 不能执行特权指令

内核态:
- 操作系统内核运行的模式
- 完全权限，可以访问所有硬件
- 可以执行特权指令

需要内核服务时（如读文件、网络通信）:
用户态 → 系统调用 → 内核态 → 完成操作 → 用户态
```

**常见系统调用**:

```
文件操作:
- open(), read(), write(), close()

进程管理:
- fork(), exec(), wait(), exit()

内存管理:
- mmap(), munmap(), brk()

网络通信:
- socket(), bind(), listen(), accept(), send(), recv()

信号:
- kill(), signal()
```

**系统调用的开销**:

```
步骤:
1. 用户态 → 陷入内核（模式切换）
2. 保存用户态上下文
3. 执行内核代码
4. 恢复用户态上下文
5. 内核态 → 返回用户态

开销:
- 模式切换: ~100-200 纳秒
- 上下文切换: 几百纳秒到几微秒

优化:
- 批量操作（一次系统调用处理多个请求）
- 使用缓冲（减少syscall次数）
- 异步IO（io_uring）
```

**Python中的体现**:

```python
# 每次调用都是系统调用
f = open("file.txt", "r")  # open syscall
for line in f:             # read syscall (内部buffered)
    process(line)
f.close()                  # close syscall

# 优化：使用缓冲
f = open("file.txt", "rb", buffering=8192)
# read()会一次读取8KB，减少syscall次数
```

### 2.6 死锁

#### 什么是死锁？

**定义**: 两个或多个进程/线程互相等待对方持有的资源，导致都无法继续执行。

**经典例子: 哲学家就餐问题**

```
5个哲学家围坐圆桌，每人面前一个盘子，每两人之间一根筷子。
吃饭需要两根筷子。

错误的实现:
每个哲学家:
1. 拿起左边的筷子
2. 拿起右边的筷子
3. 吃饭
4. 放下筷子

死锁场景:
- 哲学家0拿起筷子0
- 哲学家1拿起筷子1
- 哲学家2拿起筷子2
- 哲学家3拿起筷子3
- 哲学家4拿起筷子4

现在每个人都拿着左筷子，等待右筷子
→ 所有人都在等待，永远无法进行
```

---

#### 死锁的四个必要条件

**同时满足才会死锁**:

```
1. 互斥 (Mutual Exclusion)
   - 资源同时只能被一个进程使用
   - 例: 一根筷子同时只能被一人拿

2. 持有并等待 (Hold and Wait)
   - 进程持有资源，同时等待其他资源
   - 例: 拿着左筷子，等待右筷子

3. 不可剥夺 (No Preemption)
   - 资源不能被强制夺走，只能主动释放
   - 例: 不能抢别人的筷子

4. 循环等待 (Circular Wait)
   - 存在进程循环等待链
   - 例: P0等P1，P1等P2，...，Pn等P0
```

**破解死锁**: 破坏四个条件之一

---

#### 预防死锁

**方法1: 破坏"持有并等待"**

```
策略: 一次性获取所有资源

哲学家修改:
同时拿起两根筷子（原子操作）
如果拿不到，就都不拿

优点: 避免死锁
缺点: 资源利用率低（可能长时间等待）
```

**方法2: 破坏"循环等待"**

```
策略: 给资源编号，按序申请

哲学家修改:
筷子编号0-4
每个哲学家:
- 先拿编号小的筷子
- 再拿编号大的筷子

例子:
- 哲学家0: 先拿筷子0，再拿筷子1
- 哲学家4: 先拿筷子0（最小），再拿筷子4

不会形成循环等待

优点: 简单有效
缺点: 需要全局编号，可能不灵活
```

**方法3: 破坏"不可剥夺"**

```
策略: 设置超时，拿不到就释放已持有的

哲学家修改:
if 拿不到右筷子 (超时):
    放下左筷子
    等待一段时间
    重试

优点: 避免永久死锁
缺点: 可能活锁（livelock）—— 所有人不停重试
```

---

#### 检测和恢复

**思路**: 允许死锁发生，检测到后解除

```
检测:
1. 维护资源分配图
2. 定期检查是否有环（循环等待）
3. 有环 → 死锁

恢复:
1. 终止进程: 杀掉死锁中的某个进程
2. 资源剥夺: 强制收回某个进程的资源

选择牺牲者的策略:
- 优先级低的
- 占用资源少的
- 运行时间短的
```

---

#### AI训练中的死锁

**场景: 分布式训练**

```
问题:
GPU 0 等待GPU 1的梯度
GPU 1 等待GPU 2的梯度
GPU 2 等待GPU 0的梯度
→ 循环等待 → 死锁

原因:
- AllReduce操作的同步问题
- 不同GPU的执行顺序不同

解决:
- 确保所有GPU按相同顺序执行AllReduce
- 使用NCCL库（自动处理）
- 超时机制
```

**场景: DataLoader多进程**

```
问题:
- 主进程等待worker进程的数据
- Worker进程等待主进程的索引
- 共享资源（如文件句柄）有锁

解决:
- 设置timeout
- 正确的资源管理（及时释放锁）
- 避免在worker中共享复杂对象
```

### 3.1 网络协议栈

#### OSI七层模型 vs TCP/IP四层模型

```
OSI七层                  TCP/IP四层         常见协议
┌──────────────┐         
│  应用层       │────┐    
│  表示层       │    │     应用层        HTTP, FTP, SSH, DNS
│  会话层       │────┘    
├──────────────┤    
│  传输层       │          传输层        TCP, UDP
├──────────────┤    
│  网络层       │          网络层        IP, ICMP
├──────────────┤    
│  数据链路层    │────┐     链路层        Ethernet, WiFi
│  物理层       │────┘    
└──────────────┘

记忆口诀: 
物数网传（输）会表应
Please Do Not Throw Sausage Pizza Away
```

**每层的作用**:

```
应用层:
- 为应用程序提供网络服务
- 例: 浏览器使用HTTP

传输层:
- 端到端的可靠传输
- 端口号标识应用程序
- TCP: 可靠, UDP: 不可靠但快

网络层:
- 路由和转发
- IP地址标识主机
- 选择最佳路径

链路层:
- 同一网段内的传输
- MAC地址标识网卡
- 帧的封装和差错检测

物理层:
- 比特流的物理传输
- 电信号、光信号、无线电波
```

---

#### 数据封装过程

```
发送端:

应用层: HTTP请求
     ↓ 添加HTTP头
传输层: [TCP头|HTTP数据]
     ↓ 添加TCP头
网络层: [IP头|TCP头|HTTP数据]
     ↓ 添加IP头
链路层: [以太网头|IP头|TCP头|HTTP数据|以太网尾]
     ↓ 添加以太网帧头尾
物理层: 01010101... (比特流)

接收端: 逆向解封装
```

**关键点**:
- 每层只关心自己的协议
- 下层为上层提供服务
- 封装和解封装是对称的

### 3.2 TCP vs UDP

#### TCP (Transmission Control Protocol)

**特点**: 可靠的、面向连接的、基于字节流的传输协议

**可靠性机制**:

```
1. 序号和确认
   - 每个字节都有序号
   - 接收方确认收到（ACK）
   - 发送方超时未收到ACK → 重传

2. 流量控制
   - 接收窗口（rwnd）
   - 防止发送方发太快，接收方处理不过来

3. 拥塞控制
   - 慢启动、拥塞避免、快重传、快恢复
   - 防止网络拥塞

4. 顺序保证
   - 乱序到达的数据包会被重排序
   - 应用层看到的是有序的数据流
```

---

#### TCP三次握手

**为什么需要三次？**

```
目的: 建立可靠连接

过程:
客户端                    服务器
  │                         │
  │─── SYN (seq=x) ────────→│  第1次握手
  │                         │  服务器知道: 客户端发送正常
  │                         │
  │←── SYN+ACK (seq=y, ────│  第2次握手
  │       ack=x+1)          │  客户端知道: 双方收发都正常
  │                         │
  │─── ACK (ack=y+1) ─────→│  第3次握手
  │                         │  服务器知道: 客户端接收正常
  │                         │
  │    连接建立，可以传输数据  │
```

**为什么不是两次？**

```
两次握手的问题:

场景:
1. 客户端发送 SYN
2. SYN在网络中延迟了
3. 客户端超时，再发一次 SYN
4. 第二次SYN到达，建立连接
5. 第一次SYN（延迟的）也到达了

如果只有两次握手:
- 服务器会认为第一次SYN也要建立连接
- 分配资源，但客户端不会响应
- 浪费资源

三次握手:
- 第一次SYN到达后，服务器发SYN+ACK
- 客户端不会回复（因为是旧的）
- 服务器超时，释放资源
```

---

#### TCP四次挥手

**为什么需要四次？**

```
目的: 安全关闭连接（确保数据传输完成）

过程:
客户端                    服务器
  │                         │
  │─── FIN ───────────────→│  第1次挥手
  │                         │  客户端: "我没有数据要发了"
  │                         │
  │←── ACK ────────────────│  第2次挥手
  │                         │  服务器: "我知道了"
  │                         │  （但服务器可能还有数据要发）
  │                         │
  │←── FIN ────────────────│  第3次挥手
  │                         │  服务器: "我也没有数据了"
  │                         │
  │─── ACK ───────────────→│  第4次挥手
  │                         │  客户端: "我知道了"
  │                         │
  │   等待2MSL后关闭         │  服务器关闭
```

**为什么不是三次？**

```
TCP是全双工:
- 客户端→服务器: 一个方向
- 服务器→客户端: 另一个方向

关闭需要关闭两个方向:
- FIN + ACK: 关闭客户端→服务器
- FIN + ACK: 关闭服务器→客户端

理论上可以三次（合并第2、3次）:
但实际中，服务器收到FIN后:
- 可能还有数据要发送
- 不能立即发送FIN
- 所以ACK和FIN分开
```

**TIME_WAIT状态**:

```
为什么客户端要等待2MSL（Maximum Segment Lifetime）？

原因1: 确保ACK到达
- 客户端发送最后的ACK
- 如果丢失，服务器会重发FIN
- 客户端需要能够重发ACK

原因2: 避免旧连接干扰
- 等待网络中所有旧数据包消失
- 防止新连接收到旧数据

典型值: 2MSL = 2×2分钟 = 4分钟
```

---

#### UDP (User Datagram Protocol)

**特点**: 不可靠的、无连接的、基于数据报的传输协议

**与TCP对比**:

```
TCP                          UDP
✓ 可靠传输                   ✗ 不保证可靠
✓ 有序                       ✗ 可能乱序
✓ 流量控制                   ✗ 无流量控制
✓ 拥塞控制                   ✗ 无拥塞控制
✗ 头部大（20字节起）          ✓ 头部小（8字节）
✗ 连接开销（三次握手）        ✓ 无连接开销
✗ 速度相对慢                 ✓ 速度快
```

**UDP的优势场景**:

```
1. 实时性要求高
   - 视频会议、在线游戏
   - 宁可丢失也不要延迟

2. 简单请求/响应
   - DNS查询
   - 一个数据包就能完成

3. 广播/组播
   - IPTV、直播
   - TCP不支持广播

4. 自己实现可靠性
   - QUIC协议（HTTP/3基础）
   - 在UDP上实现选择性重传
```

---

### 3.3 HTTP协议

#### HTTP/1.1

**特点**:

```
请求-响应模型:
客户端: "给我这个页面"
服务器: "好的，这是内容"

请求方法:
- GET: 获取资源
- POST: 提交数据
- PUT: 更新资源
- DELETE: 删除资源
- HEAD: 只要头部
- OPTIONS: 查询支持的方法

状态码:
2xx: 成功
  - 200 OK
3xx: 重定向
  - 301 Moved Permanently
  - 302 Found (临时重定向)
4xx: 客户端错误
  - 400 Bad Request
  - 401 Unauthorized
  - 403 Forbidden
  - 404 Not Found
5xx: 服务器错误
  - 500 Internal Server Error
  - 502 Bad Gateway
  - 503 Service Unavailable
```

---

#### HTTP/1.1的问题

**1. 队头阻塞 (Head-of-Line Blocking)**

```
HTTP/1.1使用长连接（Keep-Alive）:
但一次只能处理一个请求:

请求1: 大文件下载（慢）──────────────────→
请求2: 小图片（快）    等待...
请求3: API调用（快）   等待...

请求2、3被请求1阻塞
```

---

#### HTTP/2

**解决方案: 多路复用**

```
一个TCP连接，多个流（stream）:

连接1:
├─ Stream 1: 请求1（大文件）─────→
├─ Stream 2: 请求2（小图片）──→
└─ Stream 3: 请求3（API）────→

并行传输，互不阻塞
```

**其他改进**:

```
1. 头部压缩（HPACK）
   - HTTP/1.1头部是文本，冗余
   - HTTP/2压缩头部

2. 服务器推送
   - 服务器主动推送资源
   - 例: 请求HTML时，主动推送CSS、JS

3. 二进制协议
   - HTTP/1.1是文本协议
   - HTTP/2是二进制，解析更高效
```

---

#### HTTP/3 (基于QUIC)

**为什么需要HTTP/3？**

```
HTTP/2的问题:
- 虽然应用层多路复用了
- 但底层还是TCP
- TCP有队头阻塞：一个TCP包丢失，整个连接阻塞

HTTP/3的改进:
- 基于UDP（QUIC协议）
- 避免TCP的队头阻塞
- 更快的连接建立（0-RTT）
- 更好的移动网络支持
```

---

### 3.4 DNS

#### DNS的作用

**域名解析**: 将人类可读的域名转换为IP地址

```
www.google.com → 142.250.185.206

为什么需要DNS?
- IP地址难记
- IP可能变化，域名不变
- 负载均衡（一个域名对应多个IP）
```

---

#### DNS查询过程

```
浏览器查询 www.example.com:

1. 检查本地缓存
   - 浏览器缓存
   - 操作系统缓存
   - 如果有 → 直接返回

2. 查询本地DNS服务器（递归查询）
   - 通常是ISP提供的
   - 如果缓存有 → 返回

3. 本地DNS服务器查询根DNS（迭代查询）
   根DNS: "我不知道，但你可以问.com DNS"
   
4. 查询顶级域DNS (.com)
   .com DNS: "我不知道，但你可以问example.com DNS"
   
5. 查询权威DNS (example.com)
   权威DNS: "www.example.com是1.2.3.4"
   
6. 返回给客户端
   - 本地DNS缓存结果
   - 客户端缓存结果
```

**递归查询 vs 迭代查询**:

```
递归查询:
- 客户端→本地DNS: "给我答案"
- 本地DNS负责找到答案

迭代查询:
- 本地DNS→根DNS: "谁知道?"
- 根DNS: "我不知道，问.com"
- 本地DNS→.com DNS: "谁知道?"
- 逐步查询，直到找到
```

---

#### DNS记录类型

```
A记录:
- 域名 → IPv4地址
- example.com → 1.2.3.4

AAAA记录:
- 域名 → IPv6地址

CNAME记录:
- 域名别名
- www.example.com → example.com

MX记录:
- 邮件服务器
- example.com → mail.example.com

NS记录:
- 权威DNS服务器
- example.com → ns1.example.com
```

### 3.5 HTTPS和TLS

#### 为什么需要HTTPS？

**HTTP的问题**:

```
1. 明文传输
   - 密码、信用卡号等敏感信息暴露
   - 中间人可以看到所有内容

2. 无法验证身份
   - 不知道服务器是不是伪造的
   - 钓鱼网站问题

3. 数据可能被篡改
   - 中间人可以修改传输内容
   - 注入恶意代码
```

**HTTPS = HTTP + TLS/SSL**

---

#### TLS握手过程（简化版）

```
目标: 协商加密密钥，验证服务器身份

客户端                        服务器
  │                             │
  │──── Client Hello ─────────→│
  │  (支持的加密算法、随机数)      │
  │                             │
  │←─── Server Hello ──────────│
  │  (选择的加密算法、随机数、     │
  │   证书、公钥)                │
  │                             │
  │  验证证书（CA签名）            │
  │  生成预主密钥                │
  │  用服务器公钥加密             │
  │                             │
  │──── 加密的预主密钥 ────────→│
  │                             │
  │  双方用随机数+预主密钥        │
  │  生成会话密钥                │
  │                             │
  │←─── Change Cipher Spec ────│
  │  (切换到加密通信)             │
  │                             │
  │──── Change Cipher Spec ───→│
  │                             │
  │    使用会话密钥加密通信        │
```

**关键点**:

```
1. 非对称加密（RSA/ECC）
   - 用于交换密钥
   - 慢，只用于握手

2. 对称加密（AES）
   - 用于数据传输
   - 快，用于正式通信

3. 证书验证
   - 证书由CA（证书颁发机构）签名
   - 客户端信任CA，从而信任服务器
   - 防止中间人攻击
```

---

#### 证书链

```
证书的信任链:

根CA证书（操作系统内置）
    ↓ 签名
中间CA证书
    ↓ 签名
网站证书（www.example.com）

验证过程:
1. 浏览器收到网站证书
2. 检查是哪个中间CA签名的
3. 验证中间CA证书（用根CA公钥）
4. 验证网站证书（用中间CA公钥）
5. 确认证书有效、未过期、域名匹配
```

### 3.6 网络性能指标

#### 延迟 (Latency)

**定义**: 数据从发送到接收的时间

**组成部分**:

```
总延迟 = 传播延迟 + 传输延迟 + 处理延迟 + 排队延迟

1. 传播延迟（光速限制）
   - 取决于物理距离
   - 光纤: ~5μs/km
   - 北京→上海（1200km）: ~6ms

2. 传输延迟
   - 取决于带宽和数据量
   - 1MB数据，100Mbps带宽: 80ms

3. 处理延迟
   - 路由器、交换机处理时间
   - 通常很小（微秒级）

4. 排队延迟
   - 拥塞时在队列中等待
   - 不确定，可能很大
```

**测量**:

```bash
# Ping: 测量RTT（往返时间）
ping google.com
# 64 bytes: icmp_seq=0 time=15.2 ms

# Traceroute: 查看路径和每跳延迟
traceroute google.com
```

---

#### 带宽 (Bandwidth)

**定义**: 单位时间内能传输的最大数据量

**单位**:
```
bps (bits per second): 比特每秒
- 1 Mbps = 1,000,000 bps
- 1 Gbps = 1,000 Mbps

注意: 1 Byte = 8 bits
- 100 Mbps 带宽
- 实际下载速度: 100/8 = 12.5 MB/s
```

**瓶颈**:

```
端到端带宽由最慢的环节决定:

你的电脑 ─ 100Mbps ─→ 路由器
                ↓
        路由器 ─ 1Gbps ─→ ISP
                ↓
          ISP ─ 10Gbps ─→ 主干网
                ↓
         主干网 ─ 10Gbps ─→ 服务器

实际带宽: min(100M, 1G, 10G, 10G) = 100Mbps
瓶颈在你的设备
```

---

#### 吞吐量 (Throughput)

**定义**: 实际传输的数据量（可能小于带宽）

**影响因素**:

```
理论带宽: 100 Mbps
实际吞吐量: 可能只有70 Mbps

原因:
1. 协议开销
   - TCP/IP头部
   - 重传机制

2. 网络拥塞
   - 丢包重传
   - 拥塞控制降速

3. 应用层限制
   - 单线程下载
   - 服务器限速
```

---

#### 带宽延迟积 (Bandwidth-Delay Product)

**定义**: 带宽 × RTT，表示"在途"的数据量

**意义**: TCP窗口大小的参考

```
例子:
带宽: 100 Mbps
RTT: 100 ms

BDP = 100 Mbps × 100 ms
    = 100 × 10^6 bits/s × 0.1 s
    = 10^7 bits
    = 1.25 MB

含义:
- 任何时刻，网络中有1.25MB数据在传输
- TCP窗口至少要1.25MB才能充分利用带宽
- 否则发送方会等待ACK，浪费带宽
```

**分布式训练中的应用**:

```
GPU间通信:
带宽: 25 GB/s (InfiniBand)
延迟: 5 μs

BDP = 25 GB/s × 5 μs = 125 KB

梯度大小: 700 MB (GPT-3)

传输时间: 700 MB / 25 GB/s = 28 ms
>> 延迟 (5 μs)

结论: 带宽是瓶颈，不是延迟
```

## 四、存储系统

### 4.1 存储层次结构

#### 金字塔模型

```
              速度 ↑  容量 ↓  成本 ↑
                   
         ┌─────────────┐
         │   寄存器     │  ~1 ns,  KB级
         ├─────────────┤
         │  L1 Cache   │  ~1 ns,  KB级
         ├─────────────┤
         │  L2 Cache   │  ~4 ns,  MB级
         ├─────────────┤
         │  L3 Cache   │  ~15 ns, MB级
         ├─────────────┤
         │  主内存RAM  │  ~100 ns, GB级
         ├─────────────┤
         │    SSD     │  ~100 μs, TB级
         ├─────────────┤
         │    HDD     │  ~10 ms, TB级
         ├─────────────┤
         │   磁带/云   │  秒-分钟级, PB级
         └─────────────┘
```

**设计原则**: 局部性原理

```
时间局部性:
- 最近访问的数据，未来可能再次访问
- 例: 循环变量

空间局部性:
- 访问某个数据，附近的数据也可能被访问
- 例: 数组遍历

利用局部性:
- 把常用数据放在快速存储（缓存）
- 按块读取（cache line, page）
```

---

### 4.2 磁盘 (HDD)

#### 机械硬盘结构

```
组成:
- 盘片 (Platter): 存储数据
- 磁头 (Head): 读写数据
- 主轴 (Spindle): 旋转盘片
- 磁臂 (Arm): 移动磁头

数据组织:
- 磁道 (Track): 同心圆
- 扇区 (Sector): 磁道的一段（最小读写单位，512B或4KB）
- 柱面 (Cylinder): 所有盘片同位置的磁道集合
```

---

#### 磁盘访问时间

```
访问时间 = 寻道时间 + 旋转延迟 + 传输时间

1. 寻道时间 (Seek Time)
   - 磁头移动到目标磁道
   - 平均: 5-10 ms
   - 占大头

2. 旋转延迟 (Rotational Latency)
   - 等待目标扇区转到磁头下
   - 平均: 半圈时间
   - 7200 RPM硬盘: 4.2 ms

3. 传输时间
   - 读取数据
   - 相对很小

总计: ~10 ms（随机访问）
```

**顺序访问 vs 随机访问**:

```
顺序访问:
- 连续读取
- 寻道一次，后续无需寻道
- 速度: ~100-200 MB/s

随机访问:
- 每次都要寻道+旋转
- 速度: ~100-200 IOPS（每秒操作数）
- 换算: 0.1-0.2 MB/s

差距: 1000倍！
```

**优化策略**:

```
1. 预读
   - 顺序读取比需要的更多数据
   - 利用空间局部性

2. 电梯算法（磁盘调度）
   - 磁头移动像电梯：先往一个方向
   - 减少寻道时间

3. 尽量顺序写入
   - 数据库日志: append-only
   - 文件系统: 连续分配
```

---

### 4.3 固态硬盘 (SSD)

#### SSD vs HDD

```
                SSD              HDD
存储介质      闪存芯片          磁盘
机械部件      无               有
随机读取      ~0.1 ms          ~10 ms
顺序读取      ~500 MB/s        ~100 MB/s
随机读写性能   相近             随机慢1000倍
耐用性        写入次数有限      几乎无限
抗震性        好               差
功耗          低               高
噪音          无               有
价格          贵               便宜
```

---

#### SSD的工作原理

**基本单位**:

```
页 (Page): 4-16 KB（读写单位）
块 (Block): 128-256页（擦除单位）

特点:
- 读写以页为单位
- 擦除以块为单位
- 必须先擦除才能写入

问题:
写入前必须擦除
→ 写放大 (Write Amplification)
```

**写放大**:

```
场景: 更新一个4KB的数据

步骤:
1. 读取整个块（512KB）到缓存
2. 修改4KB数据
3. 擦除块
4. 写回整个块

实际写入: 512KB
逻辑写入: 4KB
写放大: 512/4 = 128倍

影响:
- 性能降低
- 寿命缩短（闪存擦除次数有限）
```

**优化: 磨损均衡**

```
问题:
- 某些块频繁写入，会先损坏
- 其他块很少用，浪费

解决:
SSD控制器智能调度:
- 动态重映射
- 均匀分布写入
- 延长SSD寿命
```

---

#### TRIM命令

**问题**: 操作系统删除文件，SSD不知道

```
操作系统删除文件:
- 只是标记为"已删除"
- 实际数据还在SSD上

SSD的困惑:
- 不知道这些数据已经无效
- 后台垃圾回收时还要处理
- 影响性能

TRIM命令:
- 操作系统告诉SSD: "这些块不再使用"
- SSD可以提前擦除
- 提升后续写入性能
```

#### 文件分配方式

**1. 连续分配**

```
文件A: 块 0-9
文件B: 块 10-19

优点:
- 顺序访问快
- 简单

缺点:
- 外部碎片
- 文件增长困难
```

**2. 链式分配**

```
文件A:
块5 → 块12 → 块7 → 块20 → NULL

每个块存储指向下一块的指针

优点:
- 无外部碎片
- 文件增长容易

缺点:
- 随机访问慢（需要遍历链表）
- 指针占用空间
- 可靠性差（链断了数据丢失）
```

**3. 索引分配（现代文件系统）**

```
文件A的索引块:
┌────────┐
│ 块5    │
│ 块12   │
│ 块7    │
│ 块20   │
└────────┘

索引块存储所有数据块的地址

优点:
- 随机访问快（直接查索引）
- 无外部碎片

缺点:
- 索引块占用空间
- 大文件需要多级索引

ext4的实现:
- 12个直接块指针
- 1个一级间接块指针
- 1个二级间接块指针
- 1个三级间接块指针
支持最大16TB文件
```

### 4.5 RAID (磁盘阵列)

#### RAID的目的

```
1. 提高性能（并行读写）
2. 提高可靠性（冗余）
3. 增加容量
```

---

#### 常见RAID级别

**RAID 0 (条带化)**

```
数据分布:
磁盘0: A1 A3 A5 ...
磁盘1: A2 A4 A6 ...

优点:
- 性能翻倍（并行读写）
- 容量翻倍

缺点:
- 无冗余，一个盘坏全部丢失
- 可靠性更差（两倍故障率）

适用: 临时数据、性能优先
```

**RAID 1 (镜像)**

```
数据分布:
磁盘0: A B C D ...
磁盘1: A B C D ...（完全一样）

优点:
- 冗余，一个盘坏不影响
- 读取性能提升（可以从两个盘读）

缺点:
- 容量减半（浪费）
- 写入性能不变（要写两份）

适用: 关键数据、高可用性
```

**RAID 5 (分布式奇偶校验)**

```
数据分布:（3个磁盘）
磁盘0: A1  A2  P3  A4 ...
磁盘1: A1' P2  A3  A4'...
磁盘2: P1  A2' A3' A4"...

P = 奇偶校验块（XOR）
P1 = A1 XOR A1'

优点:
- 容量利用率高（n-1）/n
- 一个盘坏可以恢复

缺点:
- 写入慢（要计算奇偶校验）
- 两个盘同时坏，数据丢失

恢复原理:
磁盘0坏了:
A1 = P1 XOR A1'（用其他数据恢复）

适用: 平衡性能和可靠性
```

**RAID 6**

```
类似RAID 5，但有两个独立的奇偶校验块

优点:
- 可以容忍两个盘同时坏

缺点:
- 容量利用率: (n-2)/n
- 写入更慢

适用: 高可靠性需求
```

**RAID 10 (1+0)**

```
结构:
先RAID 1（镜像）
再RAID 0（条带化）

┌─────────┬─────────┐
│ RAID 1  │ RAID 1  │
│ ┌─┬─┐   │ ┌─┬─┐   │
│ │A│A│   │ │B│B│   │
│ └─┴─┘   │ └─┴─┘   │
└─────────┴─────────┘
      RAID 0

优点:
- 性能好
- 可靠性好

缺点:
- 容量减半

适用: 企业级应用
```

## 五、面试高频问题

### Q1: 进程和线程的区别？什么时候用哪个？

**回答框架**:
```
核心区别:
- 进程是资源分配单位，线程是调度单位
- 进程有独立地址空间，线程共享地址空间
- 进程间通信复杂（IPC），线程间通信简单（共享内存）
- 进程创建开销大，线程创建开销小

选择:
- CPU密集型、需要隔离 → 多进程
- CPU密集型、需要共享数据 → 多线程
- IO密集型 → 协程

Python的特殊性:
- GIL（全局解释器锁）限制
- 多线程不能真正并行执行CPU密集任务
- 需要多进程才能利用多核
```

---

### Q2: 什么是死锁？如何避免？

**回答框架**:
```
定义:
两个或多个进程互相等待对方的资源，导致都无法继续

四个必要条件:
1. 互斥
2. 持有并等待
3. 不可剥夺
4. 循环等待

避免方法:
- 破坏任一条件
- 资源按序申请（破坏循环等待）
- 一次性申请所有资源（破坏持有并等待）
- 超时释放（破坏不可剥夺）

实际经验:
- 分布式训练中，确保所有节点按相同顺序执行AllReduce
- 使用lock的timeout参数
- 避免嵌套锁
```

---

### Q3: 虚拟内存的作用是什么？

**回答框架**:
```
核心作用:
1. 进程隔离 - 每个进程独立地址空间
2. 突破物理内存限制 - Swap到磁盘
3. 简化内存管理 - 虚拟地址连续，物理可不连续

工作原理:
- 页表映射虚拟地址到物理地址
- TLB加速地址转换
- 页面置换算法（LRU）处理内存不足

AI训练中的体现:
- CUDA out of memory
- Swap导致训练变慢
- mmap加载大文件
```

---

### Q4: TCP和UDP的区别？各自适用什么场景？

**回答框架**:
```
TCP:
- 可靠、有序、面向连接
- 有流量控制和拥塞控制
- 开销大（三次握手、重传）
- 适用: 文件传输、HTTP、数据库连接

UDP:
- 不可靠、无序、无连接
- 无流量控制
- 开销小、快
- 适用: 视频会议、在线游戏、DNS

分布式训练:
- 参数同步一般用TCP（确保数据完整）
- RDMA技术可以绕过TCP，直接访问内存（更快）
```

---

### Q5: HTTP/1.1、HTTP/2、HTTP/3的区别？

**回答框架**:
```
HTTP/1.1:
- 文本协议
- 队头阻塞（一个连接一次一个请求）
- Keep-Alive复用连接

HTTP/2:
- 二进制协议
- 多路复用（一个连接多个流）
- 头部压缩
- 服务器推送
- 但TCP层面仍有队头阻塞

HTTP/3:
- 基于UDP（QUIC）
- 避免TCP队头阻塞
- 0-RTT连接建立
- 更好的移动网络支持

AI应用:
- API调用一般用HTTP/1.1或HTTP/2
- 模型推理服务考虑用HTTP/2提升性能
```

---

### Q6: 缓存一致性问题是什么？

**回答框架**:
```
问题:
- 多核CPU，每个核心有私有缓存
- 同一数据可能在多个缓存中
- 如何保证一致性？

MESI协议:
- Modified, Exclusive, Shared, Invalid四种状态
- 写入时通知其他缓存失效
- 保证最终一致性

影响:
- False Sharing: 不同变量在同一cache line
- 频繁写入共享变量导致性能下降

优化:
- Padding避免False Sharing
- 减少共享变量
- 每个线程用局部变量，最后合并

PyTorch中:
- Tensor的contiguous()和cache locality相关
```

### Q7: 什么是RAID？各级别的区别？

**回答框架**:
```
RAID目的:
- 提高性能
- 提高可靠性
- 增加容量

常见级别:
RAID 0: 条带化，性能翻倍，无冗余
RAID 1: 镜像，可靠但容量减半
RAID 5: 分布式奇偶校验，平衡性能和可靠性
RAID 10: 镜像+条带化，性能和可靠性都好但贵

选择:
- 训练数据（可重新生成）→ RAID 0
- Checkpoint（重要）→ RAID 1或RAID 5
- 生产数据库 → RAID 10
```

### Q8: SSD和HDD的区别？

**回答框架**:
```
核心区别:
- HDD: 机械磁盘，随机访问慢（~10ms）
- SSD: 闪存，随机访问快（~0.1ms）

性能:
- HDD顺序访问OK（100MB/s），随机访问差
- SSD随机和顺序都快（500MB/s）

适用:
- HDD: 冷数据、归档、大容量低成本
- SSD: 热数据、数据库、训练数据

AI训练:
- 训练数据放SSD，加速data loading
- 大型dataset可以放HDD，配合SSD缓存
```

### Q9: 什么是页面置换算法？

**回答框架**:
```
场景:
- 物理内存不够
- 需要把一些页面换出到swap

常见算法:
1. FIFO: 先进先出，简单但可能换出常用页
2. LRU: 最近最少使用，性能好但实现复杂
3. Clock: LRU的近似，实现简单性能接近

LRU思想:
- 最近用过的，未来可能还会用
- 维护访问时间
- 换出最久未访问的

应用:
- 操作系统内存管理
- 缓存系统（Redis）
- 数据库buffer pool
```

### Q10: 分布式系统中如何选择存储方案？

**回答框架**:
```
考虑因素:
1. 数据量: TB级以上考虑分布式
2. 访问模式: 随机还是顺序
3. 一致性需求: 强一致还是最终一致
4. 性能需求: 延迟和吞吐量
5. 成本: 存储和带宽费用

方案:
- 训练数据: S3/OSS（对象存储）+ 本地SSD缓存
- Checkpoint: 分布式文件系统（HDFS、Lustre）
- 元数据: 数据库（MySQL、PostgreSQL）
- 日志: 时序数据库（InfluxDB、Prometheus）

优化:
- 数据预处理，减少小文件
- 使用高效格式（Parquet、TFRecord）
- 考虑数据局部性（尽量本地读取）
```
